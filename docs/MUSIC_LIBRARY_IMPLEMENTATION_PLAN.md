# 儿歌音乐馆：基于现有代码的实施优化方案

- 文档状态：Implementation Plan
- 版本：1.0
- 更新日期：2026-11-19
- 适用范围：Childhood Library 音乐馆、音乐研究库及相关管理能力
- 依据：`main` 分支现有音乐馆页面、作品配置、试听配置、Python 脚本和音乐馆规划文档

## 1. 先明确音乐馆要建设成什么

音乐馆不是单纯的儿歌播放网站，也不是视频链接聚合页，而是一个有作品档案、版本档案、来源证据、审美评审和使用审核的儿童音乐文化图书馆。

长期定位沿用：

> 以中国经典为根，以世界经典为窗，以优秀原创为未来。

音乐馆建设分成两个相互关联但权限不同的部分：

- **音乐研究库 Research**：发现、登记、比较和研究作品、演唱版本、录音、乐谱、出版资料和来源线索。权利未知不阻断研究登记；默认保留必要元数据和来源链接，任何媒体保存行为都必须符合适用法律、来源条款和项目批准范围。
- **儿童音乐馆 Library**：对外提供经过编辑策展的作品介绍、专题目录和允许使用的资源。作品介绍、歌词/谱面展示、外链、官方嵌入、站内播放和下载分别审核，不用一个“已审核”字段代替所有使用许可。

## 2. 以现有代码为起点，不推倒重来

当前可复用的成果：

| 现有资产 | 处理建议 |
|---|---|
| `design-demos/music.html` | 保留为音乐馆首页视觉与信息架构参考 |
| `design-demos/works.html` | 保留为作品列表、筛选、详情和试听交互参考；后续拆分组件 |
| `design-demos/audio/samples.json` | 迁移为有 schema 版本的版本/试听资源数据，不继续作为长期无约束配置 |
| `design-demos/audio/official-recordings.json` | 迁移为第三方平台资源记录，保留 provider、曲目 ID、原站 URL 和条款核验信息 |
| `design-demos/audio/public-recording-collection.json` | 作为历史研究登记线索审查；不得仅凭文件元数据将其视为授权媒体 |
| `design-demos/*.py` | 逐个建立脚本清单，保留可复用的生成、导入、校验逻辑；不要整批重写 |
| MusicXML / SVG / PNG | 作为谱面与视觉资产纳入资产清单，逐项关联作品、版本、来源和权利状态 |

第一步不是把静态原型改造成大型应用，而是先为当前数据建立契约和校验，确保现有资产可迁移、可追溯。

## 3. 音乐馆领域模型：从“歌曲 + 音频”升级为作品档案

建议核心实体如下：

```text
Work（歌曲作品）
  |
  +-- WorkTitle / Alias（标准名、别名、异名）
  |
  +-- Contribution（词作者、曲作者、译配、改编等创作贡献）
  |
  +-- WorkVersion（歌词版本、语言版本、改编版本）
  |
  +-- RecordingVersion（具体演唱/录音版本）
  |      |
  |      +-- Performer / Ensemble（演唱者、合唱团）
  |      +-- Arrangement（该录音版本的编曲）
  |      +-- MediaAsset（录音文件或官方播放资源）
  |
  +-- ScoreEdition（乐谱版本）
  |      +-- MediaAsset（MusicXML、简谱、五线谱、PDF/SVG 等）
  |
  +-- SourceRecord（来源记录与证据）
  +-- RightsRecord（分对象权利记录）
  +-- EditorialReview（内容与审美评审）
  +-- CollectionMembership（专题/策展归属）
```

### 3.1 Work：作品本体

建议字段：

- `work_id`：稳定且永久的作品 ID。
- `canonical_title`、`aliases`：标准名称和别名。
- `work_type`：传统童谣、创作儿歌、校园歌曲、电影歌曲、民歌改编、摇篮曲、古典音乐等。
- `region`、`language`、`culture`：地区、语言和文化归属。
- `created_at_range`、`first_published_at`：创作和首次发表时间，可记录不确定范围。
- `summary`、`historical_context`：作品介绍和历史背景。
- `research_status`：discovered / researching / reviewed / rejected。
- `catalog_status`：candidate / curated / archived。

作品本体不直接保存某个 MP3 地址，也不因找到某个视频就将视频当作作品。

### 3.2 Contribution：创作贡献者

不要只用 lyricist / composer 两个固定字段。使用角色关联：

- lyricist（词作者）
- composer（曲作者）
- translator（译者）
- adapter（改编/译配）
- arranger（编曲）
- collector（采录者）
- editor（整理/校订）

同一作品可以有多人、多个角色；未知字段留空并标记待考，不猜测补齐。

### 3.3 WorkVersion：作品文本或创作版本

用于区分原始歌词、不同语言版本、译配版本、改编版本和校订版本。歌词权利属于具体文本版本，不应只挂在 Work 上。

### 3.4 RecordingVersion：演唱与录音版本

这是音乐馆最重要的拆分之一。每个版本至少记录：

- `recording_version_id`、`work_id`
- 演唱者、合唱团、表演者
- 录音/发行年份、专辑、唱片公司或发布机构
- 编曲者、配器、演唱形式
- 版本说明：历史原唱、童声合唱、现代翻唱、纯音乐、动画版等
- 来源页面和版本核验状态
- 对应的媒体资源 ID

**作品相同，不代表录音版本相同；现代改编版不能冒充历史首版录音。**

### 3.5 ScoreEdition：乐谱版本

乐谱必须有独立版本档案：

- 简谱 / 五线谱 / 钢琴伴奏谱 / 合唱谱 / MusicXML
- 出版社、书名、版次、ISBN、页码、编配者
- 调性、拍号、声部、谱面完整性说明
- 来源、权利状态、可展示方式

MusicXML 是可编辑的结构化谱面来源之一；SVG 是渲染结果，两者应建立派生关系，不应把 SVG 当作唯一原始谱面。

### 3.6 SourceRecord：来源证据

来源记录不只是 URL 列表。建议字段：

- `source_id`、`source_type`、`platform`、`publisher`
- `source_url`、`source_title`、`published_at`、`accessed_at`
- `supports_entity_type`、`supports_entity_id`
- `evidence_scope`：支持作品身份、作者、年代、版本、录音、谱面或权利中的哪项事实
- `evidence_excerpt_or_note`：必要且合规的证据摘要
- `confidence`：high / medium / low
- `verification_status`：unverified / checked / conflicting / rejected

一条来源可以支持多个字段，但必须明确它支持什么。**来源页面可访问不等于它证明了版权许可。**

### 3.7 MediaAsset 与 PlaybackResource 分离

- MediaAsset：实际文件或外部媒体资产，如音频、视频、图片、谱面。
- PlaybackResource：用户如何访问媒体，如 source_link、official_preview、official_embed、licensed_hosted_audio。

内部浏览器试听、开放许可示例、原创示范、第三方官方试听和授权托管必须使用不同类型，不可混在一个“音频”字段中。

### 3.8 RightsRecord：权利对象化

权利记录至少绑定：

- 权利对象：词、曲、译配、编曲、表演、录音、视频画面、封面、谱面。
- 对应作品 / 版本 / 资产。
- 权利状态：unknown / pending / verified / restricted / revoked。
- 依据、来源、权利人、许可证或授权文件。
- 地域、用途、渠道、期限、署名要求和撤回条件。
- 核验人、核验时间、复核时间。

“免费教育使用”“可在线观看”“官方上传”“平台允许嵌入”均不能自动等同于本站获得复制、托管或再发布授权。

### 3.9 EditorialReview：审美评审与儿童适宜性

作品层和录音版本层分别评审：

- 旋律美感：旋律自然、优美、是否有记忆点。
- 歌词文学性：语言是否有画面、诗意和故事。
- 童真表达：是否呈现儿童的好奇、想象和情感。
- 编曲质量：配器是否协调，音色是否过度刺激。
- 演唱表现：音准、音色、情感和合唱质量。
- 耐听程度：多次聆听是否仍有吸引力。
- 文化价值：历史、地域、民族或艺术代表性。
- 年龄适宜性：是否需要背景说明或成人陪伴。

推荐结论采用编辑标签，而不是简单分数排名：

- 核心收藏
- 文化收藏
- 扩展收藏
- 历史参考
- 暂不推荐

一首作品可以值得研究，但某个录音版本不一定适合进入核心播放推荐。

## 4. 音乐馆内容组织与前台体验

### 4.1 三大内容支柱

初期资源投入建议继续沿用：

1. 中国经典（约 55%）：经典儿童歌曲、传统童谣、校园与童年、自然与四季、动物与生命、古诗词音乐、民族与地方音乐。
2. 世界经典（约 30%）：英美童谣、欧洲经典儿童歌曲、世界摇篮曲、民族音乐、儿童古典音乐。
3. 优秀原创（约 15%）：当代原创、独立音乐人、自然主题音乐和项目原创。

这是启动期资源建设的投入建议，不是内容数量配额。

### 4.2 主题标签与作品类型分开

保留自然之歌、童年之歌、温暖之歌、世界之歌等策展主题；同时单独维护 work_type、语言、地区、年代和文化标签。主题可多选，不应替代作品类型。

### 4.3 首页建议

音乐馆首页不应只有“歌曲数量 + 分类卡片”。建议采用：

1. 音乐馆主视觉：表达“优美、自然、童真、耐听”。
2. 编辑精选：少量有完整来源与版本档案的代表作品。
3. 中国经典 / 世界经典 / 优秀原创三大入口。
4. 专题入口：自然、四季、摇篮曲、校园、地方童谣、民族音乐等。
5. 最近新增研究：明确标记为研究目录，不伪装成已审核推荐。
6. 版本发现：同一作品的历史演唱、童声合唱、现代改编等比较入口。

### 4.4 作品详情建议

详情页建议分为：

- 作品简介：创作背景、文化信息、作品身份。
- 创作者：词曲作者、译配者、采录者等。
- 版本档案：不同年代和演唱者的版本。
- 聆听入口：每个版本显示访问方式和审核状态。
- 乐谱与出版：版本、出版信息和合法访问入口。
- 编辑评审：评审的是哪个具体版本，理由是什么。
- 来源与研究记录：让资料可追溯。

不要把“播放按钮”放在每条候选作品旁边。没有合适播放资源时，作品资料仍然完整成立。

## 5. 当前 105 条作品目录的整理策略

现有 105 条作品配置应视为第一批音乐馆种子目录，而不是最终精选曲库。

建议分四个队列：

- A：优先深度研究的中国经典作品。
- B：中国传统童谣、地方民歌和民族音乐。
- C：世界经典和多语言童谣。
- D：优秀原创及当代作品。

第一批不要追求 500 条都填满。建议先挑选 20 首做完整档案样板，优先覆盖不同类型、年代、地区和版本。样板完成后再扩充到 50、100 和更大的研究目录。

《让我们荡起双桨》《我们的田野》《听妈妈讲那过去的事情》《小燕子》《卖报歌》《春游》《送别》《小白船》《采蘑菇的小姑娘》《小螺号》等可以作为候选研究锚点，但是否进入核心收藏，应以作品资料和具体录音版本的评审结果为准。

《中国儿童歌曲百年经典》500 首目录继续作为重要研究索引；目录收录不等于已完成作品身份核验、版本采集、审美评审或公开使用审核。第二、三卷目录未补齐前，不得宣称 500 首已完整建档。

## 6. 音频与播放体系：先分类，再决定怎么播放

### 6.1 五类资源必须分开

| 类型 | 用途 | 默认处理 |
|---|---|---|
| internal_local | 审核人员本机选择的本地试听 | 浏览器本地保存，不上传、不发布 |
| open_license_sample | 逐文件核验许可证的示例录音 | 记录许可证、署名、来源和文件校验值；发布前复核 |
| original_demo | 项目原创示范音频 | 明确标注原创示范、非原曲 |
| official_preview | 第三方官方短时试听 | 用户点击触发，遵守平台接口规则，不缓存 |
| licensed_hosted | 已取得对应权利的站内托管媒体 | 按授权地域、期限和用途提供服务 |

### 6.2 当前 IndexedDB 原型的定位

现有 IndexedDB 试听交互可以保留为“编辑端本地试听”能力，但要明确：

- 只保存在当前浏览器，不是中央资源库。
- 浏览器清理、设备更换或数据库损坏可能导致文件丢失。
- 存储失败降级到内存后，刷新即丢失；界面必须明确提示。
- 不得把本地试听记录显示成公共播放资源。
- 后续应补充导出/恢复提示和资源完整性检查。

### 6.3 官方短时试听

当前 Deezer 试听原型可以作为 Provider Adapter 的验证样例，但不应把 Deezer 绑定为系统唯一播放器。

统一接口建议：

- `getTrackMetadata()`
- `getOfficialPreview()`
- `getExternalPageUrl()`
- `validateProviderResponse()`

Provider 配置记录平台、曲目 ID、原站 URL、条款页面、最后核验日期、地区限制和失败回退链接。播放必须由用户主动点击触发；预览 URL 不持久化，不将短时预览等同于完整歌曲授权。

### 6.4 资源完整性

当前配置引用的音频文件必须逐一核对是否存在。建议构建检查器输出：

- 配置引用数、唯一文件数、实际文件数。
- 缺失文件、孤立文件、重复文件。
- 文件大小、格式、时长和 SHA-256（仅对允许纳入仓库/资产库的文件）。
- 对应作品 ID、版本 ID、来源记录 ID 和权利记录 ID。

权利待核验的第三方音频不得因为“原型需要试听”就默认提交到公开仓库或公开部署目录。先保留来源和必要元数据，按适用规则决定是否可保存。

## 7. 推荐技术架构

首期采用**模块化单体**，不采用微服务。

```text
Web 前台 / 编辑后台
        |
        v
API 层（FastAPI）
        |
        +-- Catalog：作品、作者、分类、专题
        +-- Versions：歌词版本、录音版本、乐谱版本
        +-- Sources：来源、证据、核验状态
        +-- Rights：权利记录与使用门禁
        +-- Reviews：审美评审、儿童适宜性
        +-- Media：资产元数据、存储和访问方式
        +-- Ingestion：人工导入、来源 Adapter、任务记录
        |
        v
PostgreSQL（结构化主数据）
        |
        +-- 文件存储（只保存允许保存的媒体）
        +-- 搜索索引（后续需要时再引入）
        +-- 任务执行（MVP 先用后台任务/命令）
```

推荐技术仍可沿用项目总方案：Vue 3 + TypeScript + Vite、FastAPI + Pydantic、PostgreSQL。初期不需要 Celery、Redis、微服务和复杂对象存储一起上；先把领域模型、迁移、导入、审核流程做稳。

- [ ] 统一作品 ID、版本 ID、媒体 ID 和来源 ID。

- [ ] 将试听资源按五类重新归类。
- [ ] 建立 20 首完整档案样板。

验收：数据可校验、引用可追溯、缺失资产可定位，旧原型仍可作为交互参考。

### M1：音乐馆领域模型与导入

- [ ] 定义 Work、Contribution、WorkVersion、RecordingVersion、ScoreEdition。
- [ ] 定义 SourceRecord、MediaAsset、PlaybackResource、RightsRecord、EditorialReview。
- [ ] 建立 JSON / CSV 导入和导出。
- [ ] 实现 ID 稳定性、重复候选检测和导入报告。

验收：一首歌可以关联多个创作者、多个演唱版本、多个乐谱版本和多个来源，且不丢失原始证据。

### M2：编辑管理 MVP

- [ ] 建立作品列表、详情和版本编辑。
- [ ] 建立来源证据编辑。
- [ ] 建立权利记录和审核状态。

验收：编辑可以从发现一首歌开始，完成身份核验、版本整理、评审和使用方式判断；未通过的媒体不会出现在公开层。

### M3：音乐馆前台重构

- [ ] 将现有静态页面迁移为 Vue 组件。
- [ ] 建立中国经典、世界经典、优秀原创入口。
- [ ] 建立专题、筛选和作品详情。
- [ ] 展示版本差异、来源和编辑评审。
- [ ] 仅对通过审核的资源显示外链、官方试听或授权播放入口。

验收：公开页面与编辑后台读取同一套数据，不再维护两份互相漂移的作品目录。

### M4：来源采集与多媒体扩展

- [ ] 人工登记与批量导入先行。
- [ ] 建立来源 Adapter 协议。
- [ ] 接入明确允许的官方 API / 开放目录。
- [ ] 增加任务日志、限速、重试和来源健康检查。
- [ ] 再评估官方嵌入与授权托管音频。

验收：采集结果进入待审核队列，不自动发布；每条记录能追溯到来源、采集任务和人工审核。

## 9. 近期建议执行顺序

1. 先做 M0：清点现有音乐数据、JSON 引用、素材缺失和脚本职责。
2. 选 20 首代表作品建立统一数据样板。
3. 用样板验证 Work / RecordingVersion / SourceRecord / RightsRecord / EditorialReview 模型。
4. 再将现有 105 条作品目录迁移进新模型。
5. 以音乐馆验证成功的模型为基础，抽象故事馆和诗词馆都能复用的公共实体。

**暂时不要做的事：** 不要先开发完整在线播放器，不要急着做自动抓取所有平台，不要把 500 首目录全部塞进前台，也不要把故事馆、诗词馆、音乐馆分别做成三套互不兼容的数据系统。
