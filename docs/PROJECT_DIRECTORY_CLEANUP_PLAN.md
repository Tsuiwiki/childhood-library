# 项目目录整改计划：以 PRD 和真实采集成果为中心

- 项目：童年书房（Childhood Library）
- 状态：整改计划，待执行
- 目标：减少文档冗余，明确唯一主版本，让项目目录直接服务于产品和内容建设

## 一、整改目标

本项目不再采用“每个阶段、每个专题、每次讨论都新增一份主文档”的方式维护。

整理后，权威信息只保留两类：

1. **产品需求（PRD）**：唯一说明产品定位、用户场景、核心功能、内容范围和验收标准。
2. **采集成果（内容数据）**：唯一说明实际收录了哪些作品、每首歌/每篇作品采集到了什么、来源在哪里、哪些内容仍缺失。

README 只做入口和状态摘要，不再承载第二套产品说明。代码目录可以保留必要的运行说明，但不能另立产品需求或采集口径。

## 二、建议的目标目录

```text
childhood-library/
├── README.md                    # 项目入口：定位、当前进度、两个权威入口
├── docs/
│   └── PRD.md                   # 唯一产品需求文档
├── data/
│   ├── music/
│   │   ├── works.json           # 儿歌作品主目录及逐曲采集结果
│   │   └── recordings.json      # 具体演唱/录音版本及播放来源
│   ├── poetry/
│   │   └── works.json           # 诗歌/诗词作品与采集结果
│   └── stories/
│       └── works.json           # 儿童故事作品与采集结果
├── assets/
│   ├── audio/                   # 实际音频资产
│   ├── scores/                  # 曲谱文件或馆藏/出版入口
│   └── images/                  # 封面、插图等资产
├── web/                         # 前端应用
├── app/                         # 后端代码（如继续保留）
├── tests/                       # 自动化测试
├── scripts/                     # 必要的数据校验、导入和资产检查脚本
└── archive/
    └── legacy-docs/              # 历史方案、批次研究文档和审计材料
```

说明：
- 上述为目标结构，不代表现在所有目录都已存在；实施时以仓库实际文件为准。
- 如果当前前端仍直接读取 design-demos 下的 JSON，先建立兼容迁移，不得直接移动导致页面空白。
- 不要求为了“目录整齐”重写后端或数据库；先让真实内容有唯一、稳定、可消费的数据来源。
- 音频等二进制文件是否进入 Git，按现有存储方式处理；目录整理不得误删 VM 上的媒体资产。

## 三、现有文档分类与处理建议

### A. 保留并重写：唯一 PRD

当前 docs/PRD.md 偏向“免费公共数字文化数据库、内容管理后台、采集系统、版权审核平台”等大平台规划，和当前首期目标存在偏差。

PRD 应重写为：
- 产品首先是一个**可以浏览、查找、播放儿歌，并了解儿歌来历和传播历史的音乐馆**。
- 用户能找到作品、听到真实且来源清楚的录音，查看作者/作曲者/创作年代/首次发表/历史版本等资料。
- 作品详情围绕“作品是什么、谁创作、何时出现、有哪些演唱版本、去哪里听、有哪些曲谱和史料”组织。
- 诗歌与儿童故事是后续扩展内容馆，不在首期稀释儿歌馆的完成度。
- 明确首期范围、核心页面、作品详情字段、播放体验、内容质量标准和验收条件。
- 不把复杂后台、自动采集平台、公共 API、用户体系和大规模版权工作流列为首期前置条件。

### B. 保留并合并：采集成果

采集成果不再以“批次 Markdown 文档”作为最终内容载体，而是按作品归档。

每首儿歌至少记录：
- 稳定作品 ID、标题、别名、类别、语言；
- 词作者、曲作者、译配/改编者、创作或发表年代（未知就留空）；
- 作品背景、历史沿革、传播与代表性演唱者；
- 具体录音版本：演唱者/团体、专辑或唱片、发行年代、来源链接、可播放方式；
- 歌词/文本来源、曲谱来源（简谱/五线谱、出版物或馆藏信息）；
- 来源名称、URL、核验备注和采集时间；
- 当前缺项及核验状态；
- 权利信息单独记录，不以“能访问”推断“可下载或可再发布”。

**计数口径必须真实：**
- 作品标题目录不等于作品资料完整；
- 找到一个网页入口不等于找到可播放音频；
- 生成音频不计为历史录音；
- 专辑页不等于逐曲音源；
- 资料缺失就明确标记，不填规则文字、模板话术或推测内容来凑完整率。

现有 specialties.json、samples.json、official-recordings.json、public-recording-collection.json、audioLinks.ts、500 首目录及各批次研究文档，先做去重、ID 对齐和字段映射，再决定如何合并。迁移前保留原始文件快照。

### C. 归档：重复的规划、审计和阶段文档

以下类别不再作为主入口长期维护：
- 项目原则、总纲、MASTER PLAN、V1 规划等重复定位文档；
- 多份音乐馆设计、实施方案、重构计划；
- 多份架构、数据库、媒体资产、采集系统设计；
- 多份路线图、实施路线、任务清单、开发进度和审计报告；
- 每次采集形成的批次 Markdown 记录。

处理方式：
1. 有价值的历史事实和决策先提取到 PRD 或作品数据中。
2. 原始批次研究文档整体迁入归档区，保留来源 URL、日期和历史证据。
3. 重复、过时且没有独立证据价值的文档，在确认已归档且无代码/链接依赖后再删除。
4. README 只链接 PRD 和采集数据，不再罗列几十份文档。

### D. 保留：运行代码必需的说明

web/README.md、app/README.md、部署/迁移说明等，如果对开发、部署、恢复确实必要，可以保留在各代码目录中。它们只解释“怎么运行和维护”，不能成为第二份产品需求或采集成果清单。

## 四、分阶段执行顺序

### Phase 1：建立文件清单和主次关系
- 列出仓库全部 Markdown、JSON、音频、曲谱、图片和脚本。
- 为每份文档标注：唯一主文档 / 可合并 / 历史证据 / 运行必需 / 可删除候选。
- 标出前端、脚本、测试对旧 JSON 和 Markdown 的引用。
- 标出 VM 上未进入 Git 的媒体资产，确认数量、路径和备份状态。
- 本阶段只盘点，不删除、不移动媒体、不改变运行中的服务。

**交付：** 一份可核对的文件迁移清单，不新增多份说明文档。

### Phase 2：重写唯一 PRD
- 以“儿歌浏览、播放、历史追溯”为首期核心。
- 将诗歌、故事明确为后续扩展。
- 收敛用户场景、页面、作品详情、播放与搜索需求。
- 删除首期不必要的大平台功能承诺。
- PRD 经确认后成为唯一产品需求基准。

**验收：** 新成员只读 PRD，就能说清楚首期做什么、不做什么，以及怎样算完成。

### Phase 3：整理唯一采集数据
- 建立统一作品 ID，去重同名作品和不同版本。
- 将分散目录、音频配置、外链、曲谱和批次资料映射到作品。
- 每个音频入口必须明确是“可直接播放”“官方试听”“外部播放页”“仅专辑/目录线索”或“失效/待核验”。
- 把历史研究中的有效事实和来源证据写入作品记录。
- 对缺失项保留明确状态，不用通用规则、采集指南和空模板代替真实内容。

**验收：** 前端能够直接读取主数据；随机抽查作品时，标题、历史资料、音频版本和来源能互相对应。

### Phase 4：归档冗余文档并更新入口
- 将历史方案、审计和批次文档归档，不立即物理删除。
- 移除 README 中过长的文档索引，改成 PRD、采集成果和开发入口。
- 清理失效链接和重复入口。
- 对确认无价值、无引用、无独立证据的重复文件再做删除。

**验收：** 项目根目录和 docs 目录没有多个互相竞争的“主计划”“主设计”“最新状态”。

### Phase 5：验证应用和数据没有退化
- 运行现有前端测试和生产构建。
- 检查作品列表、详情、搜索、播放器、专题入口。
- 检查所有媒体引用和来源链接。
- 检查历史数据迁移前后数量、ID、关联关系。
- 生成迁移前后差异清单；任何数据减少都必须有明确原因。

**验收：** 目录更简单，但原有页面、播放能力和采集成果不丢失。

## 五、整改期间的明确约束

1. 暂停新建规则文档、架构文档、采集方法论和批次总结。
2. 新采集任务的主要交付必须是作品数据和真实来源，不是新的 Markdown 说明。
3. 不为填满字段而写模板话术；没有证据就标记待核实。
4. 不把“目录条数”“链接条数”“录音配置条数”混成已完成作品数。
5. 不在未盘点引用和备份前批量删除或移动文件。
6. 不为目录整理顺手重构前后端、数据库或部署环境。
7. 每个阶段只维护一份可执行清单，完成后更新状态，不复制出新版本文档。

## 六、最终判断标准

整改完成后，用户只需要关注：
- **PRD：** 我们正在做什么产品？
- **采集成果：** 已经真正收集到了哪些作品和资料？还缺什么？
- **应用：** 能不能方便地浏览和播放这些内容？

如果某份文档不能帮助回答以上问题，也不是运行、测试或维护代码所必需，就不应继续占据项目主目录的注意力。
